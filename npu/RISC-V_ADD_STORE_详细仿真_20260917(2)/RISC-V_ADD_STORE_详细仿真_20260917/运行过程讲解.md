# ADD 与 STORE：按真实时序讲解

两个测试分别在 CPU 核心及其 ITCM/DTCM 中运行，使用代码提交 `0bca94a11eb32105ce985aa95cf3a667c9e3ac22`。没有用手绘示意图替代实际仿真。下面所有时刻来自本次 VCD。

## ADD：add x3,x1,x2

机器码 `002081B3`；目标指令位于字节 PC=0。

测试台设置 x1=`00000012`、x2=`00000023`，x3 初值=`DEADBEEF`。预期 x3=`00000035`。这些操作数由测试台在 1 ns 预置，测试重点是这一条 ADD 的硬件执行过程。

| 上升沿时刻 | 当前目标指令的进展 | 波形观察 |
|---|---|---|
| 45 ns | ITCM 输出目标指令 | inst_raw=`002081B3` |
| 55 ns | pre_decoder 预译码 | opcode_1=`33`；rs1_1=`01`；rs2_1=`02`；rd_1=`03`；func10_1=`000` |
| 65 ns | mem_buf 缓冲字段；regfile 同步读取 | opcode_2=`33`；r1_data_dec=`00000012`；r2_data_dec=`00000023` |
| 75 ns | decoder 输出执行端操作数；组合 ALU 运算 | r1_data_3=`12`；r2_data_3=`23`；alu_func4=`0`；result_4=`35`；rd_4=`03`；we_4=`1` |
| 85 ns | wb_reg 锁存写回数据与目标 | result_5=`35`；rd_5=`03`；gpr_write=`1` |
| 95 ns | regfile 在上升沿接受上一周期 WB 信号 | x3 从 `DEADBEEF` 更新为 `00000035` |

图中的 `r1_data_final_dec` / `r2_data_final_dec` 是经过旁路选择的真正操作数；本例没有在途数据冲突，所以它们与同步读取结果一致。

注意：`result_4` 是组合 ALU 输出。75 ns 这一拍，decoder 更新执行端寄存器后，ALU 同一仿真时刻产生结果，不是额外等待一拍才出结果。85 ns 的 WB 缓冲输出，要到 95 ns 才被寄存器组采样写入。因此“写回数据有效”和“寄存器存储值改变”是两个时刻。

后续 NOP 的 opcode 为 `13`，目的寄存器为 x0；它也会让 ALU 原始 we 信号保持高。图里的 `gpr_write = we_5 && (rd_5 != 0)` 排除了对 x0 的无效写入，可准确看到仅有的一次有效通用寄存器写入。

讲解稿：

“先看取指输出，45 ns 得到 ADD 的机器码。下一拍把它拆成两个源寄存器 x1、x2 和目的寄存器 x3，opcode 是 33，功能码是加法。65 ns 同步读出两个操作数 12 和 23，这些数在图中都是十六进制。75 ns 它们进入执行端，组合 ALU 算出 35。85 ns 结果先进入写回缓冲，目的寄存器编号和有效写使能也同时到位。最后在 95 ns 上升沿，x3 真正从原先的 DEADBEEF 更新成 35。”

自动检查：最终结果正确；恰好一次 x3 有效写回；源寄存器不变；没有内存写入；x0 保持为 0。

## STORE：sw x2,12(x1)

机器码 `0020A623`；目标指令位于字节 PC=0。

测试台设置 x1=`00800000`、x2=`12345678`，DTCM[3] 初值=`DEADBEEF`。偏移量 12 是十进制，即十六进制 `0C`。

| 上升沿时刻 | 当前目标指令的进展 | 波形观察 |
|---|---|---|
| 45 ns | ITCM 输出目标指令 | inst_raw=`0020A623` |
| 55 ns | 预译码选择 LSU 路径 | lsu=`1`；opcode_lsu_1=`23`；func10_lsu_1=`002`；rs1_1=`01`；rs2_1=`02`；offset_store0_1=`0C` |
| 65 ns | 同步读出基址、写数据；形成有效地址 | r1_data_lsu=`00800000`；r2_data_lsu=`12345678`；offset_store0_2=`0C`；有效字节地址=`0080000C` |
| 75 ns | LSU 寄存输出完整写请求 | bus_addr=`00200003`；bus_data=`12345678`；bus_be=`F`；bus_we=`1` |
| 85 ns | DTCM 采样上一周期写请求并更新存储单元 | DTCM[3] 从 `DEADBEEF` 更新为 `12345678`；bus_we 同时回落 |

有效地址计算：

```text
字节地址 = x1 + 立即数
         = 0x00800000 + 0x0000000C
         = 0x0080000C

项目内部总线使用字地址：
bus_addr = 字节地址 >> 2 = 0x00200003
```

本版 DTCM 根据字地址的高位识别地址区域，并使用低 12 位选择数组下标；所以此请求写入 `dtcm[3]`。SW 写入一个 32 位整字，四个字节都使能，`bus_be = 4'b1111`，在图中以十六进制 `F` 显示。

STORE 的地址加法在 LSU 路径完成，不经过 ADD 的 `u_alu` 算术写回路径。STORE 没有目的通用寄存器，所以 `gpr_write` 始终为 0，图中的 x3 始终保持 `DEADBEEF`。

讲解稿：

“这是一条 SW，它要把 x2 的数据写到 x1 加 12 的位置。55 ns 的译码结果选择访存路径，给出基址寄存器 x1、写数据寄存器 x2，以及偏移量 0C。65 ns 读出基址和数据，地址相加得到 0080000C。项目内部总线传的是字地址，所以右移两位后是 00200003。75 ns 地址、写数据、四个字节使能和写使能一起输出，并保持一个周期。85 ns 的上升沿，DTCM 接收这笔写请求，把第 3 个字的内容更新为 12345678。STORE 写的是内存，因此没有通用寄存器写回。”

自动检查：恰好一次写入；采样时地址、数据、字节使能全部正确；DTCM[3] 最终值正确；相邻两个字不变；没有有效 GPR 写回；源寄存器和 x0 不变。

## 阅读波形的两个细节

1. 两次测试都在 40 ns 释放复位，45 ns 才出现目标指令输出。45 ns 之后的 PC 已经推进到 4，因为 PC 和 ITCM 在同一上升沿使用旧值，再分别更新输出；此时 inst_raw 仍是地址 0 取出的指令。这不是错取了地址 4 的指令。
2. 本版只有一个全局 `stage` 控制状态，它描述正常执行、暂停或冲刷，不是单条指令的流水级编号。图片顶部按真实模块数据推进时刻标记“取指输出、预译码、读寄存器、ALU/总线输出、写回/内存更新”，不能把这些标题当成 RTL 新增的状态信号。

`effective_byte_addr` 是测试台观察别名，等于 LSU 最终基址加上 STORE 偏移量；`bus_byte_addr = bus_addr << 2` 只用于解释字地址；`memory_word` 与 x3 是实际存储单元的观察别名。这些信号均没有驱动或修改 CPU 功能。
